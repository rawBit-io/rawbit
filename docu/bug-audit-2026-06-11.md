# rawbit code audit — full bug report

**Date:** 2026-06-11
**Scope:** entire codebase on `main` (frontend `src/` ~40.7k lines TS/TSX, backend `backend/` ~6.4k lines Python), plus the two bugs found during the hex-to-flow work on `feature/hex-to-flow`.
**Method:** multi-agent audit — 18 area-specific finder agents (tabs/persistence, Flow core ×2, share/file ops, flow lib, node ops, node components, undo/snapshot, layout/UI, dialogs/help, misc libs/hooks, backend API/security, calc_func ×2, backend graph, race/timing sweep, parse/persist sweep, app shell) produced 72 raw findings, deduplicated to 59 (plus 4 from a re-run of the crashed backend-API finder). Every finding was then put before an adversarial verification panel of 3 independent agents with distinct lenses — *refute* (try to disprove against the code), *trigger* (trace real-world reachability), *mechanism* (check evidence, line numbers, and the proposed fix). A finding is confirmed with ≥2 real-votes. 56 findings were panel-verified (55 at 3/3, one at 2/3); 7 findings whose panels were cut off by API session limits were verified manually, link by link, against the code. **Every claim below survived verification; 0 findings were refuted** — write-ups were corrected where verifiers found inaccuracies, and those corrections are included as reviewer notes.

After merging two write-ups of the same root bug (RB-01), the audit confirms **62 distinct findings**: 1 critical, 12 high, 28 medium, 21 low.

> **Remediation status (2026-06-11):** all 62 findings are fixed on `main`'s working tree, following each finding's proposed fix as refined by its reviewer notes. Two adjacent defects discovered during remediation were fixed alongside: the frontend opcode catalogue mirrored RB-03's stray `OP_2` (`src/lib/opcodes.ts`), and `ErrorPanel` shared RB-50's nested-button key handling. Every fix carries a regression test; verified green: frontend unit/integration suite (593 tests, was 546 at baseline), backend suite (298 tests, was 284), `tsc`, `eslint`, and the Playwright e2e suite (chromium and firefox fully green on full runs; webkit green in isolation, with a few load-flaky specs under 3-browser parallel runs — including `file.accessibility.spec.ts:121`, which fails identically on the unfixed tree and is pre-existing). One e2e fixture (`connect-copy-skip.json`) was updated: it relied on the phantom contiguous-fallback port that RB-40 removes (its `node_target` declared `numInputs: 3` but only two structured fields); the fixture now declares the third field explicitly, preserving the test's omitted-notice semantics.

## Part I — The two bugs found during the hex-to-flow work

These were found, root-caused, and fixed on the `feature/hex-to-flow` branch (6 commits ahead of `main` at the time of writing); they are documented here for the record. Both fixes live on that branch only.

### HX-1 — Rebuilt flows opened unfitted (viewport race on new-tab creation)

- **Severity:** high · **Category:** race-condition · **Status:** fixed on `feature/hex-to-flow`
- **Where:** `src/components/Flow.tsx` (`handleRebuiltFlow`, line ~1974 on the branch), `src/hooks/useTabs.ts` (`addTab`, line ~961 on the branch), `backend/flow_generator/legacy_builder.py:785`

**Symptom.** When a rebuilt flow opened in its new tab, the canvas sometimes stayed at the default viewport (zoom 1, origin top-left). With a flow spanning ~11,000×4,000 px the user saw two or three header nodes and empty canvas. The render e2e caught it immediately: only 3 of 45 nodes in the DOM.

**Root cause.** A race between two viewport writers. `handleRebuiltFlow` called `scheduleExampleFlowFit()` after creating the tab — a retry ladder (0–800 ms) that stops retrying as soon as one `fitView` succeeds, typically at the 0 ms tick. Meanwhile `addTab` created the tab hard-coded with `transform: {x: 0, y: 0, zoom: 1}` and immediately called `runViewportRestore(newTab, …)`, which applies that identity transform on the next animation frame. Whoever ran last won: the fit usually landed first, declared success and cancelled its retries — then the tab restore's rAF overwrote it with identity. Pure frame-ordering, hence intermittent (pass/fail/pass across identical e2e runs).

The shared-flow import path had met the same race earlier and worked around it with `settle: true` (keep re-fitting through the whole 800 ms window). That shrank the failure window but did not close it: under load (parallel Playwright workers) the tab restore can fire after 800 ms, and then nothing corrects it.

**Fix (at the source, not the symptom).** The generator now ships a viewport in the flow JSON (`legacy_builder.py:785`, `flow["viewport"] = {…}`), anchored on the info card at a readable zoom. `handleRebuiltFlow` validates it (finite x/y, zoom > 0) and passes it into tab creation via a new optional parameter: `addTab({ transform: viewport })`. Since the tab is born with the right transform, the tab restore — the very mechanism that used to clobber the fit — now applies the generator's viewport itself. There is no second writer to race. Verified with 7 consecutive green runs of the render spec (previously failing roughly every other run). Side benefit: the tab opens on the "Rebuilt transaction" info card (txid, per-input signing modes, fee) and reads left-to-right like a lesson.

**Related on `main`:** RB-37 (`useTabs.ts:855`) is the same family — uncancelled `fitView` retry timers from a previous restore clobbering the next tab's viewport — and remains unfixed on `main`.

### HX-2 — Node overlaps below multi-row constants (layout pitch too uniform)

- **Severity:** medium · **Category:** layout/logic-error · **Status:** fixed on `feature/hex-to-flow`
- **Where:** `backend/flow_generator/legacy_builder.py:71-73` and band-height arithmetic (~lines 334-345)

**Symptom.** The overlap check in the render e2e flagged colliding node pairs in all three fixtures — e.g. in the 4-input mainnet flow, four identical collisions, one per input band.

**Root cause.** The layout engine placed rows on a uniform 430 px pitch (`ROW`, taken from the hand-made lessons' spacing). But identity nodes grow with their configured text rows: a `rows=3` constant (funding raw-tx hex, redeemScript) renders ~700 px tall, a `rows=2` one (signature, pubkey) ~560 px. Anything placed exactly one `ROW` below such a node sat inside it: the vout field under each tall funding rawTX constant; the SIGHASH flag under the private key / redeemScript in signing chains; the pubkey row under the signature row in wire-mode P2PKH clusters; stacked data pushes in decomposed multisig/P2SH scriptSigs. The unit-level layout-hygiene test only asserted that no two nodes share the same position — it could not see rendered heights; only measuring real DOM bounding boxes exposed the overlaps.

**Fix.** Size-aware row pitches: `ROW_AFTER_2 = 1.4 × ROW` and `ROW_AFTER_3 = 1.7 × ROW` for any node placed below a 2-row/3-row constant, applied at every stacked position, plus band heights recomputed from the same arithmetic so bands cannot bleed into each other. Verified by regenerating the fixtures and re-running the overlap check: zero overlapping pairs across all three flows (45, 77, and 48 nodes).

## Critical severity

### RB-01 — Auto-refresh reload overwrites every inactive tab's archive with the active tab's canvas

- **Location:** `src/hooks/useAutoRefreshVersion.ts:123`
- **Also reported as:** `src/components/Flow.tsx:1302` — "Pre-reload save loop overwrites every inactive tab's archive with the active tab's canvas" (same root bug, found independently by a second finder; merged here)
- **Category:** data-loss
- **Verification:** adversarial panel, run 1 — 2/2 verifiers confirmed

**Description.** triggerReload loops over ALL tabs and calls saveTabData(tab.id) with no data option. saveTabData (src/hooks/useTabs.ts:749-750) sources the snapshot from getNodes()/getEdges(), which in Flow.tsx:856-857 return nodesRef/edgesRef — the single live canvas, i.e. the ACTIVE tab's graph. The only guard is the version check at useTabs.ts:774 ('if (!force && tabVersion === graphRevRef.current) return'), which skips the already-saved active tab but lets every inactive tab through whenever its stored version differs from the active tab's current revision (the normal case). Each inactive tab's entry.raw, its compressed payload, and its localStorage key rawbit.flow.tab.<id> are then overwritten with a clone of the active tab's nodes/edges before window.location.reload() fires. After reload, every flow tab contains a copy of the active flow; the original contents are permanently destroyed (the per-tab keys were rewritten).

**Trigger.** Deploy a new app version (hourly /healthz poll sets rawbit:needsReload at useAutoRefreshVersion.ts:209-211), then a user with 2+ flow tabs backgrounds the browser tab for ≥60s and returns — the visibilitychange handler (lines 145-171) calls triggerReload, clobbering all inactive tabs, then reloads.

**Evidence.**

````text
useAutoRefreshVersion.ts:122-127:
      tabs.forEach((tab) => {
        if (tab?.id) {
          saveTabData(tab.id);
        }
      });
useTabs.ts:749-750:
      const rawCurrentNodes = options?.data?.nodes ?? getNodes();
      const rawCurrentEdges = options?.data?.edges ?? getEdges();
useTabs.ts:773-776:
      const tabVersion = idx >= 0 ? tabs[idx].version : undefined;
      if (!force && tabVersion === graphRevRef.current) {
        return;
      }
Flow.tsx:856-857:
  const getSavedNodes = useCallback(() => nodesRef.current, []);
  const getSavedEdges = useCallback(() => edgesRef.current, []);
````

**Proposed fix.** In triggerReload, save only the active tab: pass the active tab id down (e.g. add activeTabId to AutoRefreshArgs and call saveTabData(activeTabId) once, with { force: true, immediate: true } so the synchronous encode lands before location.reload()). Alternatively/additionally, make saveTabData refuse to snapshot the live canvas for a tabId that is not the active tab unless options.data is provided.

**Reviewer notes.**
- Minor refinements only: the function invoked per tab is the saveTabDataGuardingSharedImport wrapper (Flow.tsx:1231-1243), which adds no inactive-tab protection; and on the worker compression path the localStorage clobber races against reload navigation commit (it is guaranteed only on the synchronous no-worker fallback, useTabs.ts:732-736), so persistence of the corruption is highly likely but not strictly deterministic. The proposed fix is sound; saving only the active tab with { force: true, immediate: true } also fixes a secondary flaw — the current non-immediate save may not even persist the active tab's edits before reload.
- Minor nuance, not a flaw in the finding: the default persistence path compresses via an async worker (useTabs.ts:706-739), so each inactive tab's localStorage overwrite races window.location.reload(). In practice the writes land (the document keeps running tasks until the navigation commits, far longer than a worker round trip), and when worker construction fails (caught at useTabs.ts:1321-1323) the fallback encodes and persists synchronously, making the clobber deterministic. The proposed fix is correct; note the active-tab save should indeed use { force: true, immediate: true } since the current call also relies on the async worker path landing before reload.
- (on the duplicate write-up) Two minor nuances, neither changing the verdict. (1) Permanence is not guaranteed per tab: with no options, saveTabData routes through the async compression worker, so the corrupted localStorage write races window.location.reload(); a tab's archive survives if navigation commits before the worker round-trip. The synchronous fallback (worker unavailable or postMessage throws, useTabs.ts:731-736) persists immediately, and in practice the old document stays alive long enough for worker messages to land, so data loss is realistic but per-tab probabilistic rather than certain — severity critical still fits. (2) The guard line is useTabs.ts:774 (claim cited 773-776, which contains it). Conversely, inactive tabs whose stored version coincidentally equals the active rev (e.g., all-fresh version 0 tabs with no edits) are skipped, as the claim already qualifies.
- (on the duplicate write-up) One nuance: in the default (non-immediate) save path the compression goes through a web worker (useTabs.ts:706-738), so the corrupting localStorage write races the reload — it usually lands because location.reload() doesn't halt JS while the new document is fetched, and it is fully synchronous (guaranteed) whenever the worker is unavailable or postMessage throws (fallback at lines 732-736). So corruption is highly probable but not 100% deterministic per occurrence; severity remains critical since it is permanent, silent data loss.
- (on the duplicate write-up) One nuance: in the common path compressTabArchive offloads compression to a Web Worker (useTabs.ts:706-731), so the localStorage write for the corrupted inactive-tab archive lands asynchronously and races with the synchronous window.location.reload() — it is only deterministic via the synchronous fallback (worker missing or postMessage throws, useTabs.ts:731-736). The in-memory archive overwrite is unconditional and the code's intent is to persist, so the data-loss bug is real, but actual on-disk corruption is timing-dependent rather than guaranteed on every trigger; severity could arguably be high rather than critical.

## High severity

### RB-02 — script_verification's fallback dummy transaction is unparseable, breaking the documented optional-tx mode

- **Location:** `backend/calc_functions/calc_func.py:2846`
- **Category:** logic-error
- **Verification:** adversarial panel, run 2 — 3/3 verifiers confirmed

**Description.** When vals[2] (tx hex) is empty, script_verification substitutes a hard-coded dummy transaction that carries the segwit marker+flag (00 01) but has zero inputs and therefore zero witness records. The project's python-bitcointx fork (site-packages bitcointx/core/__init__.py ~line 1166) raises ValueError('Superfluous witness record') whenever the witness flag is set but all witness stacks are empty, so CTransaction.deserialize rejects the dummy every time. The function then re-raises 'Invalid transaction hex: Superfluous witness record' before any script execution happens. Consequence: the documented standalone script-debugging mode (docstring: "vals[2] – (optional) full raw transaction hex" / "Provide a dummy tx if none was supplied") is 100% broken — every Verify Script node whose tx_hex field is left blank (the node's shipped default is inputs.vals = ["","","","0","",""] in src/components/sidebar-nodes.ts) and every /bulk_calculate API call omitting the tx errors out with a cryptic message instead of tracing the script. Reproduced end-to-end through bulk_calculate_logic: errors = [{'nodeId': 'n1', 'error': 'Invalid transaction hex: Superfluous witness record'}]. None of the existing tests cover the empty-tx path (all pass a tx_hex).

**Trigger.** Drag the 'Verify Script' node from the sidebar, enter any scriptSig/scriptPubKey, leave the tx_hex field blank (its shipped default), and let the flow calculate; or POST /bulk_calculate with a script_verification node whose vals[2] is empty.

**Evidence.**

````text
calc_func.py 2845-2856:
2845:    if not tx_hex:
2846:        tx_hex = (
2847:            "010000000001"  # version 1 | marker+flag
2848:            "00"            # 0 inputs
2849:            "00"            # 0 outputs
2850:            "00000000"      # lock-time
2851:        )
2853:    try:
2854:        tx = _deserialize_tx_cached(tx_hex)
2855:    except Exception as e:
2856:        raise ValueError(f"Invalid transaction hex: {str(e)}")

Vendored fork bitcointx/core/__init__.py:
            if wit.is_null():
                # It's illegal to encode witnesses
                # when all witness stacks are empty.
                raise ValueError('Superfluous witness record')

Repro: script_verification(["", "51"]) -> ValueError: Invalid transaction hex: Superfluous witness record
````

**Proposed fix.** Replace the segwit-flagged 0-input dummy with a legacy-serialized 1-input/1-output dummy that the fork accepts, e.g.:

    if not tx_hex:
        tx_hex = (
            "01000000"            # version 1 (legacy, no marker/flag)
            "01" + "00" * 32 +    # 1 input, null prevout hash
            "ffffffff"            # prevout index
            "00"                  # empty scriptSig
            "ffffffff"            # sequence
            "01" + "0000000000000000" + "00"  # 1 output, 0 sats, empty script
            "00000000"            # lock-time
        )

Verified: this hex deserializes (vin=1, vout=1) under the vendored bitcointx and also makes inIdx=0 valid so legacy CHECKSIG demos can compute a sighash instead of erroring.

### RB-03 — 2OF3_MULTISIG_SUFFIX template emits a stray OP_2, producing structurally invalid (unspendable) multisig scripts

- **Location:** `backend/calc_functions/opcodes.py:29`
- **Category:** logic-error
- **Verification:** adversarial panel, run 2 — 3/3 verifiers confirmed

**Description.** A 2-of-3 CHECKMULTISIG script is OP_2 <33B pk1> <33B pk2> <33B pk3> OP_3 OP_CHECKMULTISIG, so with 2OF3_MULTISIG_PREFIX = "5221" (OP_2 + PUSH(33)) already supplying the m=2 opcode, the tail after the last key must be "53ae" (OP_3 OP_CHECKMULTISIG). ## Part III — Cross-cutting themes

Most of the serious findings are instances of five structural patterns. Fixing the pattern fixes the class.

### 1. One live canvas, many writers (the data-loss class)

`saveTabData(tabId)` with no explicit data snapshots `getNodes()/getEdges()` — which are **always the active tab's live canvas** (`Flow.tsx:856-857`). Any caller that passes an inactive tab id silently persists the active tab's graph under the inactive tab's key. RB-01 (auto-refresh reload loop) is the catastrophic case; RB-05 (`reapplyPendingSharedGraph`), RB-11/RB-34 (snapshot scheduler writing into the wrong tab's history), and RB-20 (intro-drop animation) are the same shape. **Class fix:** make `saveTabData` refuse to snapshot the live canvas for a non-active tabId unless `options.data` is provided (one guard kills the whole class), then fix each caller to pass explicit data or the active id.

### 2. Scheduled callbacks without ownership (the Bug-HX-1 family)

Retry ladders, rAF restores, and debounced persists are started per tab but never cancelled or ownership-checked when the tab changes underneath them: RB-37 (fitView retry timers), RB-34 (rAF snapshot into previous tab), RB-62 (workspace reset undone by in-flight writers), and HX-1 itself. **Class fix:** a per-tab generation counter — every scheduled viewport/persist/snapshot callback captures the generation at schedule time and aborts if it changed at fire time.

### 3. Ports that exist nowhere (the invisible-edge class)

`buildPorts` is the source of truth for the Connect dialog and flow validation, but not for what nodes actually render — so the dialog happily wires edges to handles that have no DOM element. React Flow then cannot draw them (invisible, unselectable, undeletable), while the backend either silently drops the value (multi-val: only `_visible_field_indices` are read) or silently consumes it (single-val: any edge overrides the typed value). RB-40 (phantom `numInputs` fallback ports), RB-28 (identity 'INPUT VALUE'), RB-55 (Trezor dropdowns). **Class fix:** derive connectability and validation from one shared predicate that matches the render rules (no port for `options` fields, none when `numInputs === 0`, no contiguous fallback when an `inputStructure` exists), and reject/strip edges whose `targetHandle` resolves to no rendered handle.

### 4. Version counters that are not monotonic where code assumes they are

`graphRevRef` is rewound on tab switch while `revTick` React state is not (RB-19: a numeric collision silently suppresses autosave); the tab counter is re-derived from a hydration fallback that ignores existing ids (RB-38: tab-id collision overwrites another tab's archive); a one-time migration marks itself done before tab data hydrates (RB-22). **Class fix:** per-tab saved-revision bookkeeping instead of rewinding the global counter; derive counters from observed maxima; gate one-time migrations on hydration completion.

### 5. Backend robustness gaps on adversarial or merely malformed input

Element-shape validation is missing behind the list-type check (RB-18 / RB-17 → 500s with stack-trace logging); graph sentinels leak across runs (`_cycle` RB-04, timeout-path sentinels RB-46); the Redis budget tracker assumes Redis never fails after startup (RB-15) and its registry set never shrinks (RB-16); crafted flows can freeze frontend validation itself (RB-13). None of these compromise funds or secrets — the backend handles no private keys server-side — but all are cheap availability/robustness wins.

### Silent-failure UX (recurring small pattern)

Several confirmed bugs share "the action did nothing and told the user nothing": quota error permanently disables saves (RB-36), failed shared-link retry is a no-op (RB-33), the MuSig2 '+' button no-ops at the 10th pubkey (RB-54), OpCode removal deletes the wrong entry (RB-25). When fixing, prefer an error surface (toast/banner) over silent `return`.
