# rawbit code audit — full bug report (2026-06-16)

**Date:** 2026-06-16  
**Scope:** entire codebase on `main` **except `src/my_tx_flows/`** — frontend `src/` (~42.8k lines TS/TSX) + backend `backend/` (~6.7k lines Python).  
**Method:** multi-agent adversarial audit per [`periodic-bug-audit-playbook.md`](periodic-bug-audit-playbook.md). Area-scoped finder agents (hard cap 7 findings each, no fixing), each fed the prep pack: the 62 already-fixed prior findings (`RB-01..RB-62`) and the 7 batch-1 findings as out-of-scope, the structural [pattern library](bug-patterns.md), and the new-code hotlist (ECIES, OP_RETURN extract, hex-to-text, copy-paste group parenting, undo-coalesce, Safari group-edge rework). Every deduplicated finding was then put before a **3-agent verification panel** with distinct lenses — *refute* (disprove from the code, default not-real), *trigger* (trace real-world reachability), *mechanism* (check evidence / line-numbers / fix). **Quorum ≥2 real-votes confirms.** Verifier corrections are recorded under each finding (they are part of the record — fix to the corrected mechanism, not the original wording).

**Run note (honesty).** This audit ran in two passes. Pass 1 launched 26 finders concurrently; 18 of them — exactly the ones over the largest files and the whole backend — were killed by the harness 180s idle-timeout while reasoning silently over 1.5k–4.2k-line files, so pass 1 only completed 8 areas (→ NB-01..NB-07). Pass 2 (the "recovery run") re-audited the remaining 20 areas with explicit *grep-then-windowed-read* instructions (and `sidebar-nodes.ts` split into three line-range slices); all 20 completed with no stalls (→ NB-08..NB-34). Findings are numbered `NB-NN` continuously across both passes and grouped below by severity, not by pass.

**Result: 34 confirmed findings — 0 critical, 4 high, 18 medium, 12 low.** 11 further findings were reported by finders but did not reach panel quorum; they are listed in the [Dropped findings](#dropped-findings-did-not-reach-quorum--refuted-registry-seed) registry so future audits do not re-pay their discovery cost.

### NB-01 — Single global pending/coalesce refs are shared across all tabs; an edit on tab B abandons tab A's still-pending after-calc snapshot (lost undo step + stale stored snapshot)

- **Location:** `src/hooks/useSnapshotScheduler.ts:102-112 (pendingTokenRef/pendingTabIdRef/coalesceTokenRef/coalesceLabelRef), :281-289 (markPendingAfterDirtyChange overwrites pendingTabIdRef), :343-358 (tab-mismatch early return keeps token pending), :370-417 (after-calc uses single global token)`
- **Category:** data-loss · **Severity:** high · **Area:** snapshot-undo
- **Dedup key:** `useSnapshotScheduler.ts:cross-tab-shared-pending-coalesce-refs`
- **Verification:** panel 2/2 — refute ✗, trigger ✓, mechanism ✓

**Description.** All of the scheduler's after-calc bookkeeping — pendingSnapshotRef, pendingTokenRef, lastSnapshotTokenRef, coalesceLabelRef, coalesceTokenRef, and pendingTabIdRef — are single useRef values, NOT keyed per tab (only snapshotFramesRef is a per-tab Map). The after-calc effect's tab-mismatch guard at :345-358 is designed to KEEP a tab A edit pending ('the snapshot fires with the right content when the user returns to that tab') when the user switches away before that tab's 500ms-debounced recalc (useCalculation.ts:42) settles. But the recovery relies on those shared refs surviving until the user returns. As soon as the user makes ANY dirty-producing edit/delete on tab B, markPendingAfterDirtyChange (:282-284) unconditionally bumps pendingTokenRef to a new value and overwrites pendingTabIdRef to 'B'. When tab B's recalc settles, the after-calc effect runs with currentTabId===pendingTabId==='B', captures token T2, and clears coalesce refs (:389-390). Tab A's pending token T1 no longer equals pendingTokenRef, pendingTabIdRef is now 'B', and pendingSnapshotRef has been set false — so tab A's pending after-calc is permanently abandoned. Consequence: tab A's edit never produces its 'After calc' history entry, and if the edit was a delete, the structural 'Node(s) removed' entry that scheduleSnapshot pushed BEFORE the recalc retains the pre-recalc graph (stale downstream results computed from the just-deleted node, since the recalc results were supposed to be folded in by replaceState/coalesce). Undoing/redoing to that entry restores a snapshot with wrong cached results, and the user silently loses one undo step for tab A's action. This is the multi-tab generalization of the RB-11 fix: that fix added the tab guard, but the single shared refs collide the moment the other tab is also edited within the recalc window.

**Trigger.** On tab A, delete a node that has downstream consumers (or edit a field). Within ~500ms (before the debounced recalc round-trip settles), switch to tab B and make any edit/delete there. Tab B snapshots correctly; tab A's after-calc is dropped — its 'Node(s) removed' history entry keeps the stale pre-recalc state and no 'After calc' step is recorded for tab A.

**Evidence.**

```text
useSnapshotScheduler.ts:102 `const pendingTokenRef = useRef(0);` :108 `const coalesceTokenRef = useRef<number | null>(null);` :112 `const pendingTabIdRef = useRef<string | null>(null);` (all single refs). :282-284 `pendingTokenRef.current += 1; pendingSnapshotRef.current = true; pendingTabIdRef.current = getActiveTabId?.() ?? null;` (unconditional overwrite). :350-352 comment `// Keep the token pending — the snapshot fires with the right content when the user returns to that tab.` :370 `const token = pendingTokenRef.current;` :387-390 `const coalesceInto = coalesceTokenRef.current === token ? coalesceLabelRef.current : null; coalesceLabelRef.current = null; coalesceTokenRef.current = null;` :416-417 `pendingSnapshotRef.current = false; lastSnapshotTokenRef.current = token;`
```

**Proposed fix.** Key the after-calc bookkeeping per tab. Replace pendingSnapshotRef/pendingTokenRef/lastSnapshotTokenRef/coalesceLabelRef/coalesceTokenRef/pendingTabIdRef with a Map<tabId, {pending, token, lastToken, coalesceLabel, coalesceToken}> (mirroring snapshotFramesRef), so markPendingAfterDirtyChange, armAfterCalcCoalesce, and the after-calc effect read/write the entry for the tab that owns the edit (the pending tab) rather than a single global slot. The after-calc effect should iterate/flush the entry matching the currently active tab, leaving other tabs' pending entries intact until the user returns to them.

**Verifier corrections.**
- (trigger) Minor imprecision in wording: it is not literally a 'lost undo step' in count — the 'Node(s) removed' entry still exists and the deletion remains undoable; what is lost is the coalesced after-calc correction, so that entry permanently holds stale downstream results (dirty:false, so undo/redo won't recompute them). Also note the live canvas and tab A's stored archive ARE repaired on return because the archived dirty nodes re-fire the recalc; only the per-tab undo HISTORY snapshot remains stale. Severity high is reasonable for the silent history data-correctness divergence.
- (mechanism) The proposed fix is directionally correct (per-tab keying mirroring snapshotFramesRef) but understates scope: pendingSnapshotRef is part of the public SnapshotScheduler interface and is read/written directly by external callers (Flow.tsx:2964/3209/3277 and useFlowInteractions.ts:174/909/919/932). It cannot simply be 'replaced with a Map' — those callers must be migrated to a tab-keyed API (e.g. markPending/isPending(tabId)) or a façade keyed by the active tab must be kept, otherwise the drag-stop and other paths that set pendingSnapshotRef.current=false would break. Severity 'high' is reasonable: silent loss of an undo step plus a persisted snapshot carrying stale post-delete downstream results.

### NB-02 — Failed TrezorConnect.init() caches a rejected promise, permanently disabling all Trezor actions for the session

- **Location:** `src/lib/trezor/connect.ts:81-97 (assignment line 82-88, cached await line 90)`
- **Category:** logic-error · **Severity:** high · **Area:** trezor
- **Dedup key:** `connect.ts:initpromise-rejection-not-cleared`
- **Verification:** panel 2/2 — refute ✓, trigger ✗, mechanism ✓

**Description.** ensureInitialized() memoizes the init call in the module-level `initPromise` and only ever assigns it when it is null (line 82: `if (!initPromise)`). TrezorConnect.init() returns Promise<void> and rejects on common transient/blocked-startup conditions (popup blocked by the browser, no device/transport available at init time, network/iframe load failure, manifest rejected). When it rejects, `initPromise` is left holding the *rejected* promise. There is no `.catch` that resets it back to null on failure (confirmed: grep of the whole src tree shows initPromise is assigned in exactly one place and never cleared). Consequently every subsequent call to getTrezorAddress() / signTrezorTransaction() does `await initPromise` (line 90), re-throws the same stale rejection, and the user can never successfully run a Trezor action again without a full page reload — even after they fix the underlying cause (plug the device in, allow the popup, reconnect). This is the same 'sentinel/cache written on the error path and never cleared, permanently disabling the feature' failure mode as RB-04 and RB-36, but it is a distinct, un-audited instance in the Trezor init lifecycle. Note: clearing on rejection is the correct fix because a *failed* init leaves the SDK uninitialized, so re-calling init() is valid (unlike re-calling after a *successful* init, which the SDK rejects).

**Trigger.** User drops a 'Trezor Get Address' (or 'Trezor Sign Transaction') node, clicks Get Address while the connect popup is momentarily blocked or no device is attached -> init() rejects. User then allows popups / plugs in the Trezor and clicks Get Address again: still fails with the stale error, and stays broken for the rest of the tab's lifetime.

**Evidence.**

```text
let initPromise: Promise<void> | null = null;
...
async function ensureInitialized() {
  if (!initPromise) {
    initPromise = TrezorConnect.init({
      manifest: buildManifest(),
      coreMode: getCoreMode(),
      popup: true,
    });
  }

  await initPromise;   // line 90 — re-awaits the SAME rejected promise on every later call

  if (!manifestRegistered) {
    TrezorConnect.manifest(buildManifest());
  }

  manifestRegistered = true;
}
// init type (node_modules/@trezor/connect/lib/types/api/init.d.ts): InitType = (settings) => Promise<void>  -> rejects on failure
```

**Proposed fix.** Reset the cache on failure so a retry can re-init: `if (!initPromise) { initPromise = TrezorConnect.init({...}); initPromise.catch(() => { initPromise = null; }); }` (or wrap the await in try/catch that nulls initPromise before re-throwing). Only the rejected promise is cleared; a resolved one stays cached so init() is never called twice on success.

**Verifier corrections.**
- (refute) Minor: 'high' severity is somewhat generous given this only affects the niche Trezor hardware flow and requires a transient init failure to trigger; medium would be more proportionate. The mechanism, line numbers, trigger, and 'broken until page reload' consequence are all accurate.
- (mechanism) Two minor inaccuracies, neither affects the bug: (1) the init() assignment spans lines 83-87, not the cited 82-88 (line 82 is the `if (!initPromise)` guard). (2) The evidence comment cites node_modules/@trezor/connect/lib/types/api/init.d.ts, but the actual import is @trezor/connect-web; its init still returns Promise<void> and delegates to the same throwing impl, so the type claim holds.

### NB-08 — History-load deferred setEdges has no tab-ownership guard: undo on one tab writes its restored edges onto another tab after a switch

- **Location:** `src/components/Flow.tsx:3226-3251 (deferred setEdges at 3243-3250), generation bump at 3201, tab-switch early-return at 3189-3194`
- **Category:** data-loss · **Severity:** high · **Area:** flow-core-a
- **Dedup key:** `flow.tsx:history-load-deferred-setedges-no-tab-guard`
- **Verification:** panel 3/3 — refute ✓, trigger ✓, mechanism ✓

**Description.** The history-load effect restores an undo/redo snapshot by calling setNodes(restoredNodes) synchronously and then deferring the edge restore. When a restored edge references a target handle index >= the target node's totalInputs (hasMissingHandle === true, the normal case when undoing past an input-count change), the edge write is pushed two frames out via requestAnimationFrame -> setTimeout(0) -> setEdges(restoredEdges) (lines 3243-3250). The ONLY guard on that deferred write is historyRestoreGenRef.current !== restoreGen (lines 3227, 3245). historyRestoreGenRef is incremented ONLY at line 3201, which is reached only AFTER the skipLoadRef early-return at lines 3189-3194. A tab switch (selectTab in useTabs.ts sets skipLoadRef.current = true at line 969 before swapping the live nodes/edges via baseSetNodes/baseSetEdges and flipping activeTabId), so when the history-load effect re-runs for the newly active tab it early-returns at line 3189 and NEVER bumps the generation. Consequently a deferred setEdges scheduled by tab A's undo still passes its generation guard after the user has switched to tab B, and writes tab A's snapshot edges onto tab B's LIVE canvas. The generation guard was the RB-21 fix for same-tab undo/redo interleave; it has no tab-ownership (activeTabId) check, and the deferred timer is not tracked in any ref array so nothing cancels it on tab switch/unmount. Because setEdges -> setEdges wrapper (Flow.tsx:971-993) calls incRev -> incrementGraphRev which bumps revTick (Flow.tsx:621-628), the stray write also triggers the autosave effect (dep revTick at Flow.tsx:2761), persisting tab B's corrupted edge set to its archive. loadingUndoRef is already reset to false in a separate rAF (line 3267) by the time the setTimeout fires, so onEdgesChange offers no protection either.

**Trigger.** On tab A, undo (Ctrl/Cmd+Z) to a snapshot whose edges include a targetHandle index that meets the hasMissingHandle condition (e.g. undo across a change that reduced a multi-input node's input count). Immediately click another tab (tab B) before the deferred edge restore lands (a ~1 frame + macrotask window). Tab B's edges are overwritten with tab A's restored edges and then autosaved.

**Evidence.**

```text
Flow.tsx:3241-3250: `if (hasMissingHandle) { requestAnimationFrame(() => { setTimeout(() => { if (historyRestoreGenRef.current !== restoreGen) return; setEdges(restoredEdges); }, 0); }); } else { setEdges(restoredEdges); }`. Flow.tsx:3189-3194 (tab-switch path): `if (skipLoadRef.current) { skipLoadRef.current = false; lastLoadedPtr.current = pointer; return; }` — returns before the generation bump at Flow.tsx:3201 `historyRestoreGenRef.current += 1;`. useTabs.ts:966-994 selectTab sets `skipLoadRef.current = true;` then `baseSetNodes(clone(nextArchive.nodes)); baseSetEdges(clone(nextArchive.edges));`. setEdges wrapper Flow.tsx:986-988 calls `incRev()` on change; incrementGraphRev Flow.tsx:627 `setRevTick((tick) => tick + 1);` feeds the autosave effect (Flow.tsx:2758-2765 deps include revTick).
```

**Proposed fix.** Capture the restore's tab id in the effect (const restoreTabId = activeTabId) and re-check it inside both deferred callbacks before writing: bail if activeTabIdRef.current !== restoreTabId, in addition to the generation check. Additionally bump historyRestoreGenRef (or set a cancellation flag) on the skipLoadRef early-return path so a tab switch invalidates any in-flight restore, and track the setTimeout id in a ref that the effect cleanup / a tab-change cleanup clears.

**Verifier corrections.**
- (mechanism) Minor, non-load-bearing nits only — the finding is otherwise accurate:
1) incRev is at Flow.tsx:952 (`const incRev = useCallback(() => incrementGraphRev(), [incrementGraphRev])`); the finding referenced it generically without a line.
2) The finding pins the tab-switch early-return on line 3189 (skipLoadRef path). That is the expected path since selectTab sets skipLoadRef=true, but note a second early-return at line 3195 (`lastLoadedPtr.current === pointer`) would also skip the gen bump if tab B's pointer coincidentally equals the last-loaded pointer. Either way the generation is not bumped, so the conclusion is unchanged.
3) The base edge state comes from useNodeOperations() (Flow.tsx:774-790), worth noting as the reason the deferred write hits the shared live canvas; the finding called it the "LIVE canvas" without naming the source.

### NB-09 — validateFlowData never validates edge sourceHandle against the source node's output ports

- **Location:** `src/lib/flow/validate.ts:373-489 (edge loop); collectHandleMetadata at 81-93`
- **Category:** validation · **Severity:** high · **Area:** flow-lib
- **Dedup key:** `src/lib/flow/validate.ts:source-handle-not-validated`
- **Verification:** panel 3/3 — refute ✓, trigger ✓, mechanism ✓

**Description.** The edge-validation loop validates the TARGET handle exhaustively (EDGE_TARGET_NO_INPUTS, EDGE_TARGET_HANDLE_MISSING, EDGE_TARGET_HANDLE_UNKNOWN at lines 455-488) but performs NO validation of the edge's sourceHandle. For `source` it only checks the id is a known node (lines 395-409). collectHandleMetadata (lines 85-87) deliberately collects ONLY `ports.inputs` handle ids into validHandles and discards `ports.outputs`. But nodes can have multiple, distinctly-handled outputs: buildPorts (src/lib/nodes/ports.ts:24-33) emits one output per `data.outputPorts[i].handleId`, and per `extract_tx_field` dynamic field as `output-<index>`. An imported/shared/stale flow whose edge carries a sourceHandle that no longer matches any rendered output port (e.g. a tx-extract field was deleted, or outputPorts reordered) passes validation with ok:true. The backend then resolves the wrong/absent value: graph_logic.py:437/523/588 call `_resolve_upstream(get_res, e['source'], e.get('sourceHandle'))` which uses sourceHandle to pick the output. Result: a flow that validates clean computes a WRONG or empty value (and the edge can also silently fail to render in React Flow). This is the source-side dual of RB-09/RB-30 and is exactly the 'ports that exist nowhere' pattern.

**Trigger.** Import (file open or shared link) a flow containing an edge whose source node is a multi-output node (a node with data.outputPorts, or extract_tx_field in dynamic mode) and whose sourceHandle is `output-7` (a port index that does not exist / was removed). validateFlowData returns ok:true; on calculation the backend resolves the wrong output port, producing a wrong or missing result with no validation feedback.

**Evidence.**

```text
validate.ts:402 `} else if (!nodeIds.has(source)) {` — only existence is checked; grep over validate.ts for 'sourceHandle' / 'outputs' returns zero matches inside the edge loop. collectHandleMetadata: `ports.inputs.forEach((input) => { if (input.handleId) handles.add(input.handleId); });` (validate.ts:85-87) — outputs never read. backend graph_logic.py:437 `_resolve_upstream(get_res, e["source"], e.get("sourceHandle"))`.
```

**Proposed fix.** Extend HandleMetadata to also collect output handle ids (from buildPorts(node).outputs), keyed by source node. In the edge loop, after resolving the source node's metadata, normalizeHandle(edge.sourceHandle); if the source node has any non-empty output handle ids and the normalized sourceHandle is non-empty but not in that set, emit an error (e.g. EDGE_SOURCE_HANDLE_UNKNOWN). Treat an empty/absent sourceHandle as the default single output (consistent with ports.ts handleId === '').

**Verifier corrections.**
- (refute) Minor precision fix to the Description/Result wording: for the primary trigger (a removed or out-of-range port such as output-7) the backend get_res returns None (an empty/absent value), not a different existing output's value — see graph_logic.py:694-696 which returns None when handle not in outputValues rather than falling back to data['result']. A genuinely 'wrong' (different but present) value only arises when the stale sourceHandle happens to collide with another still-present output id (e.g. after a reorder). The proposed fix (collect output handle ids into HandleMetadata keyed by source node, emit EDGE_SOURCE_HANDLE_UNKNOWN when a non-empty normalized sourceHandle isn't among them, treating empty/absent as the default single output consistent with ports.ts handleId === '') is sound and addresses both cases.
- (mechanism) Finding is accurate; only a minor non-load-bearing addendum. The HandleMetadata map is constructed/stored at validate.ts:289-290 (`const meta = collectHandleMetadata(node); handleMeta.set(node.id, meta);`), and looked up in the edge loop at line 455 (`const meta = handleMeta.get(target);`). The finding cited collectHandleMetadata at 81-93/85-87 (correct) but did not mention the build site — this does not affect the verdict. The "RB-09/RB-30" cross-references could not be verified as they are tracker labels, not code, but no code claim depends on them. Implementation note for the fix: it should collect buildPorts(node).outputs handleIds keyed by SOURCE node (collectHandleMetadata currently keys validHandles by node for inputs and is already stored per-node in handleMeta, so extend HandleMetadata with e.g. `outputHandles: Set<string>` populated from ports.outputs, then in the edge loop look up handleMeta.get(source) and validate normalizeHandle(edge.sourceHandle) against it).

### NB-03 — buildPorts enumerates group inputs only from groupInstanceKeys, never falling back to groupInstances count, so the Connect dialog offers no targets for rendered handles on un-migrated/legacy nodes

- **Location:** `src/lib/nodes/ports.ts:66-84 (groups/instanceKeys loop); diverges from render src/components/nodes/calculation/CalculationNodeView.tsx:787-796 and src/lib/nodes/fieldUtils.ts:80-83`
- **Category:** logic-error · **Severity:** medium · **Area:** calc-mutations
- **Dedup key:** `ports.ts:group-inputs-ignore-groupinstances-fallback`
- **Verification:** panel 3/3 — refute ✓, trigger ✓, mechanism ✓

**Description.** buildPorts (the SOLE source of connectable ports for the Connect dialog via useConnectPorts) derives group input handles exclusively from `data.groupInstanceKeys[title]` (ports.ts:67 `const instanceKeys = data.groupInstanceKeys ?? {}`, ports.ts:70-71 `const bases = instanceKeys[group.title] ?? ## Cross-cutting themes

The new findings cluster into the same structural classes as the prior audit (see [`bug-patterns.md`](bug-patterns.md)); fixing the class is cheaper than fixing each instance.

1. **Tab-ownership on scheduled / deferred writes (data-loss class — patterns 1 & 2).** The single most serious recurring class. NB-08 (history-load deferred `setEdges` has no active-tab guard and writes a restored snapshot onto whichever tab is now active), NB-01 (snapshot scheduler's after-calc bookkeeping is global, not per-tab) and NB-24 (file import applies the parsed graph to the live canvas with no active-tab guard) are all the RB-01/RB-11/RB-34 shape: a write that should target the tab that *initiated* it instead targets the *currently active* tab. **Class fix:** capture the owning tab id at schedule/initiation time and re-check `activeTabIdRef.current === ownerTabId` (plus a per-tab generation counter) before every deferred/async write; track timers so a tab switch cancels them.

2. **Ports/handles that exist nowhere — now the source side too (pattern 3).** RB-09/RB-28/RB-40/RB-55 covered target-side phantom ports; this audit adds the source side and the inverse. NB-09 (`validateFlowData` never checks `sourceHandle` against the source node's outputs), NB-03 (group inputs enumerated only from `groupInstanceKeys`, so legacy nodes offer no Connect target for rendered handles), NB-34 (dead `hasOutputHandle:false` flag) and NB-19 (bundle fan-out spacing suppressed for all siblings). **Class fix:** one shared predicate that derives connectability/validation from the render rules, applied to *both* endpoints of every edge.

3. **Stale values surviving structural change (pattern 6).** NB-04 (`setTxFieldExtractField` leaves the previous `outputValues[output-i]`), NB-12 (dynamic tx-field-extract leaves stale multi-output values on calc error), NB-23 (regression of RB-26 — GroupNode title edit lost on viewport unmount). **Class fix:** clear the companion value/edge in the same operation that changes structure; commit in-progress edits on unmount.

4. **Backend robustness & resource bounds on adversarial input (pattern 8).** The in-memory budget tracker leaks a `_Window` per distinct IP (NB-10) and has a check-then-record race (NB-25) and an expensive rejection path (NB-11); dynamic tx-extract trusts an unbounded `txExtractFields` count (NB-26); `validateFlowData` bounds `numInputs` but not `inputStructure`/`groupInstanceKeys` (NB-18); `taproot_sighash_default` still throws an opaque `struct.error` on out-of-range values (NB-27, sibling of RB-14); `extract_tx_field` rejects `0x`-prefixed hex it should accept (NB-28). **Class fix:** bound every attacker-controlled count/size; validate shape and surface typed errors rather than letting `struct`/parse throw.

5. **Cryptographic correctness in the new ECIES / verify path (crypto class).** NB-13 (`verify_signature` normalizes high-S to low-S *before* verifying, so it silently accepts malleated signatures an educational tool should flag) and NB-14 (ECIES is a raw HMAC-keystream stream cipher with no integrity tag and a deterministic-ephemeral-key reuse hazard). These are new-feature design issues, medium severity, but worth resolving before the feature is taught as canonical.

6. **React context/value identity churn (perf, pattern-adjacent to RB-07).** `SnapshotContext` (NB-17) and `FlowActionsContext` (NB-31) hand a fresh object to consumers on every `Flow` render, re-rendering every node (NB-17 even mid-drag). **Class fix:** `useMemo` the context value on stable deps.

7. **Ownership on demo / animation rAF loops (pattern 2).** Help demos run unbounded `requestAnimationFrame` retry loops with no demo-ownership check (NB-20, NB-21) — the same family as the RB-20 intro-drop and the known `Flow.selectionMode` flake.

8. **Markdown rendering (pattern 9).** Inline code spans aren't protected from emphasis/link processing (NB-22) and the block-stash sentinel collides with user text (NB-32) — the same regex-ordering family as RB-60/RB-61.

3. Hybrid policy:
   - Keep production ECIES random.
   - Require deterministic ECIES inputs in committed lesson fixtures.

**Status:** confirmed, unfixed  
**Gate impact:** blocks `npm test`

**Evidence.**

- `src/my_tx_flows/p5_P2SH_and_OP_Return.json` contains `edge_xRTVL33s` targeting `node_k87GKtyf` with `targetHandle: "input-3100"`.
- The target node's output group fields expose indexes `3000`, `3010`, and `3020`; `3100` is not a rendered input field.
- `npm test` reports `EDGE_TARGET_HANDLE_UNKNOWN`.

**Suggested fix.**

1. Inspect `node_k87GKtyf` in the flow editor or JSON.
2. Replace `targetHandle: "input-3100"` with the actual intended rendered input handle.
3. Re-run the flow integrity test.

**Regression verification.**

- `npm test -- src/lib/__tests__/flowDataIntegrity.test.ts`
- `npm test`

### CODEX-OOS-02 - P5 flow has stale or non-reproducible committed goldens

**Scope:** out of scope for the flow data file; related in-scope test-policy issue is CODEX-03  
**Status:** confirmed, unfixed  
**Gate impact:** blocks `pytest backend/tests`

**Evidence.**

- `pytest backend/tests/test_flow_goldens.py -q` fails on `p5_P2SH_and_OP_Return.json`.
- The failure reports 24 committed golden values that do not reproduce.
- Mismatches include ECIES output and downstream transaction/signature/script-debug values.

**Suggested fix.**

1. First decide and implement the ECIES fixture policy from CODEX-03.
2. Fix the invalid P5 handle from CODEX-OOS-01.
3. Refresh P5 goldens only after the graph is structurally valid and ECIES entropy is deterministic or explicitly exempted.
4. Review the JSON diff manually before committing.

**Regression verification.**

- `pytest backend/tests/test_flow_goldens.py`
- `pytest backend/tests`
- `npm test -- src/lib/__tests__/flowDataIntegrity.test.ts`
